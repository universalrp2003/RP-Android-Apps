# Disable and suspension research — 0.3.0 follow-up

## Scope and evidence

This is a focused survey of Android documentation, Android 16 AOSP source and public device reports, not a survey of the entire web. Vendor modifications and firmware versions can differ. The exact candidate and observed stock emulator and owner-phone results are in [the compatibility record](appdisabler-0.3.0-compatibility-evidence.md). No new candidate, manufacturer ROM validation, or owner-phone test is implied here.

## High-priority correctness issue in the existing candidate

On AOSP Android 16, [`pm suspend`](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/pm/PackageManagerShellCommand.java) calls the suspension API, prints the **resulting aggregate suspended state**, and returns exit 0 even when that state is false. The underlying [`SuspendPackageHelper`](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/pm/SuspendPackageHelper.java) may refuse, for example, the active launcher. Conversely, `pm unsuspend` can print true if another actor still suspends the package. The candidate currently treats exit 0 and no leading `Error` as successful without checking that state, and its local note can then be incorrect. This is a source-based defect finding, **not evidence that Joyose's reported suspension failed**. Also review disable/enable success checks: success needs a requested-state readback, not exit status alone.

Android has a public [`PackageManager.isPackageSuspended(packageName)`](https://developer.android.com/reference/android/content/pm/PackageManager#isPackageSuspended(java.lang.String)) since API 29. The candidate's comments claiming no public way to query suspension are incorrect; the loader currently uses only a local preference. Test this API on stock and OEM devices, including package visibility exceptions and profiles. API 26–28 need a supported fallback with explicit **unknown** where no trustworthy readback exists. An app-local note records an action by this app, not current state or which actor owns a suspension. Android 11+ [package visibility filtering](https://developer.android.com/training/package-visibility) also makes “not found” potentially ambiguous. AOSP supports suspensions from multiple actors; never claim that unsuspend succeeded while aggregate suspension remains true, and don't promise to remove another policy's restriction.

A disposable stock 15/16 probe is defined in `.github/workflows/appdisabler-suspension-research.yml` and `tools/appdisabler-suspension-research.py`. [Run 43534742085](https://github.com/universalrp2003/RP-Android-Apps/actions/runs/43534742085) passed on both Android 15 and 16: the fixture's normal suspend and unsuspend returned the expected states, and after the fixture became the active HOME role, suspension returned exit 0 with `new suspended state: false`. The fixture alone was modified; this does not establish the candidate's UI behavior, verify the public suspension API, modify an owner's phone, or prove behavior on an OEM. The sandbox could inspect job conclusions but could not download the raw log; the workflow's assertions encode these outcomes.

## Persistence

AOSP Android 16's package manager schedules a delayed restriction write (10 seconds) for normal enabled-state updates, while the `SYNCHRONOUS` flag invokes the write synchronously. `pm disable-user` supplies flags 0; suspension changes also schedule a restriction write. Sources: [package manager](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/pm/PackageManagerService.java), [shell](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/pm/PackageManagerShellCommand.java), [suspension helper](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/core/java/com/android/server/pm/SuspendPackageHelper.java). This is a plausible explanation for inconsistent immediate-emulator-reboot results, **not a proven root cause**; the emulator reboot is not a physical power-menu reboot.

The public [enabled-setting API](https://developer.android.com/reference/kotlin/android/content/pm/PackageManager#setApplicationEnabledSetting(kotlin.String,kotlin.Int,kotlin.Int)) accepts `SYNCHRONOUS` (API 30+, background thread), but changing other packages requires sufficient privilege. Shizuku's shell execution does not make the ordinary app call privileged automatically. Android's hidden `IPackageManager` also exposes `flushPackageRestrictionsAsUser`; AOSP 16 checks user/cross-user constraints. Its compatibility, shell permission, behavior on old Android and OEMs, failure modes, and durability have **not** been validated. Avoid hardcoded Binder transaction numbers and don't ship either approach as a guarantee. Prototype privileged calls against disposable fixtures, compare immediate reboot to unmodified baseline, test restore, then test OEMs. A successful flush must not be treated as evidence the requested state was accepted, nor as protection from power loss or vendor policies.

## Semantics and proposed design

1. Represent **enabled/disabled**, **suspended/not suspended/unknown**, and **running/not seen/unknown** separately; provide separate disabled and suspended counts. A process observation is a snapshot, and absent `ps` access is unknown. `FLAG_STOPPED`, persistent flag and a grey Force stop button aren't proof of a process's current state. Shared UID/process and OEM visibility may complicate attribution.
2. Validate the exact requested result after every operation; on ambiguous or unrecognized output, show unknown/failure, not a success toast. Prefer public suspension query for visible packages on API 29+, with verified shell output as additional evidence, not `pm list packages -e/-d` or a guessed dumpsys flag. Check current user rather than assuming user 0; test work/secondary profiles before claiming support. For recovery, distinguish suspension by the shell from restrictions by other actors.
3. Suspension limits access but is not equivalent to full disable; force-stop is best effort. Android lists protected roles and other unsuspendable packages in [DevicePolicyManager](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#setPackagesSuspended(android.content.ComponentName,%20java.lang.String%5B%5D,%20boolean)); the policy API is not evidence that this app has device-owner privileges. Show useful denial details and don't automatically uninstall packages or circumvent device protections.
4. Stage a small, independently tested fix. Test parsing and exception paths, external state changes, multiple suspenders, data-clear/reinstall, Android 26–28 and 29+, profile handling, denylisted fixture, disable/suspend/restore and reboot. Then obtain a **new** release APK and owner hash-matched test before publication. Preserve the currently owner-tested APK separately: a rebuild is different bytes.
5. For device coverage, record model, firmware/build, Android version, profile, Shizuku mode, candidate SHA and per-operation evidence. Stock emulators are not One UI, ColorOS, OxygenOS or HyperOS; actual physical/device-farm testing is still needed. Do not claim universal compatibility.

## Xiaomi reports, not a universal workaround

A public [Brevent issue](https://github.com/brevent/Brevent/issues/902) contains HyperOS shell denial reports and a purported vendor code excerpt; it is not official documentation or proof that every Xiaomi build behaves identically. Some community scripts recommend uninstalling for user 0 or changing system settings. Those have different risks and restoration limitations and are **not** an automatic fallback for this app. The owner's Joyose observation remains as recorded; neither that observation nor these reports establishes reboot persistence or other-device compatibility.
